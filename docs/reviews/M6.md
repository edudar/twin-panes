## 1. Findings by Severity

### Critical (P0)

1. **`Conflict.isSameItem` misses case-insensitive, symlinked, and Unicode-equivalent
   self-copies, trashing the source file** (`[Resolved in 7f5b3a0]`)
   - [Conflict.swift](../../TwinPanesKit/Sources/TwinPanesCore/Conflict.swift#L23-L25),
     [TreeCopier.swift](../../TwinPanesKit/Sources/TwinPanesCore/TreeCopier.swift#L123-L131)
   - `isSameItem` compares `item.source.standardizedFileURL.path ==
     existing.standardizedFileURL.path`. On case-insensitive APFS (`Docs/a.txt` vs
     `docs/a.txt`), symlinked parents (`/tmp` vs `/private/tmp`), or NFC/NFD equivalents,
     `isSameItem` returns `false`, `Conflict.choices` offers `.replace`, and
     `TreeCopier.copyItem` trashes `target` (the source itself) before `copyFile` fails
     with `ENOENT`.
   - **Fix:** Use `BookmarkStore.pathsEqual(item.source, existing)` in
     `Conflict.isSameItem`, and add a defensive guard in `TreeCopier.copyItem` refusing
     `.replace` when `conflict.isSameItem` is `true`.

2. **`ObservationToken` calls `MainActor.assumeIsolated` from non-isolated `deinit`** (`[Resolved in d8de87b]`)
   - [FileOperationQueue.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationQueue.swift#L26-L32),
     [QueuedOperation.swift](../../TwinPanesKit/Sources/TwinPanesCore/QueuedOperation.swift#L104-L108)
   - `ObservationToken` is `Sendable` (non-isolated) and runs `cancel()` in `deinit` on
     whichever thread drops the last reference. `FileOperationQueue.observe(_:)` supplies
     `MainActor.assumeIsolated { _ = self?.observers.removeValue(forKey: id) }`. If an
     observer (such as `OperationsStripViewController`, which has no `isolated deinit`) is
     released off the main thread, `deinit` traps (`_dispatch_assert_queue_fail`).
   - **Fix:** Hop to the main actor asynchronously (`Task { @MainActor [weak self] in
     _ = self?.observers.removeValue(forKey: id) }`) inside `ObservationToken`'s cancel
     closure.

3. **Deadlock / permanent hang when cancelling or quitting (`⌘Q`) while waiting on a
   conflict sheet** (`[Resolved in d8de87b (core), 9ace114 (app)]`)
   - [FileOperationQueue.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationQueue.swift#L68-L76),
     [FileOperationQueue.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationQueue.swift#L196-L212),
     [FileOperationCommands.swift](../../TwinPanes/FileOperationCommands.swift#L43-L54),
     [AppDelegate.swift](../../TwinPanes/AppDelegate.swift#L249-L262)
   - `ConflictBridge.answer(for:)` blocks the worker thread on `ready.wait()` until
     `ConflictSheet.ask(on:)` returns. `operation.cancel()` only sets
     `OperationControl.isCancelled` and never dismisses the open sheet or signals `ready`.
   - Quitting via `stopForQuit()` cancels running ops and awaits `operation.finished()`,
     hanging `.terminateLater` forever. Any programmatic cancel while `.waitingForAnswer`
     permanently wedges the serial `turnHolder` queue and leaks the worker thread,
     `SecurityScope` tokens, and `FileOperationQueue`.
   - **Fix:** Register a cancel handler on `QueuedOperation` / `ConflictBridge` that ends
     the active conflict sheet via `window.endSheet(_:returnCode:)` and signals
     `ConflictBridge` with `.stop`.

### High (P1)

4. **Cross-volume/conflict folder moves lose moved children on partial move and break Undo
   on folder Merge** (`[Resolved in f674749]`)
   - [TreeMover.swift](../../TwinPanesKit/Sources/TwinPanesCore/TreeMover.swift#L72-L75),
     [TreeCopier.swift](../../TwinPanesKit/Sources/TwinPanesCore/TreeCopier.swift#L233-L241),
     [FileOperationHistory.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationHistory.swift#L14),
     [FileOperationHistory.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationHistory.swift#L46-L47)
   - (a) On a partial folder move (`EXDEV` or `EEXIST`) where `src/docs/x.txt` moves but
     `src/docs/y.txt` fails/skips/cancels, `src/docs` stays on disk (`ENOTEMPTY`). Because
     `copy.created` only recorded top-level `src/docs` and `TreeMover` filters
     `copy.created` by `metadata(of: made.source) == nil`, `outcome.moved` stays empty and
     Undo cannot put `x.txt` back.
   - (b) Conversely, on a folder **Merge** move where all children move and `removeSources`
     deletes empty `src/docs` (and nested empty folders), `outcome.moved` only lists leaf
     files (`src/docs/x.txt -> dest/docs/x.txt`), so `PutBack` (`⌘Z`) fails with `ENOENT`
     trying to rename back into the deleted `src/docs`.
   - **Fix:** Derive `outcome.moved` from the top-most items actually removed by
     `removeSources` (recording moved children whenever a parent folder stays behind), and
     have `PutBack` create missing ancestor directories before renaming back.

5. **`PutBack` treats `.merge` as `.skip`, drops cross-volume cancellation & progress, and
   ignores `applyToAll`** (`[Resolved in f674749]`)
   - [PutBack.swift](../../TwinPanesKit/Sources/TwinPanesCore/PutBack.swift#L14-L44),
     [PutBack.swift](../../TwinPanesKit/Sources/TwinPanesCore/PutBack.swift#L56-L58),
     [PutBack.swift](../../TwinPanesKit/Sources/TwinPanesCore/PutBack.swift#L79-L86)
   - `Conflict.choices` offers `.merge` for folder conflicts, yet `PutBack` hits
     `case .skip, .merge: return true` and silently leaves the folder in
     Trash/destination with 0 failures.
   - Cross-volume `PutBack` passes `progress: { _ in }`, drops `moved.wasCancelled`
     (continuing to later items instead of stopping), ignores `ConflictAnswer.applyToAll`,
     and checks same-path via `standardizedFileURL.path`.
   - **Fix:** Implement folder `.merge` back (Decision #2), forward
     `progress`, propagate `moved.wasCancelled`, remember `applyToAll` per kind, and use
     `BookmarkStore.pathsEqual`.

6. **`OperationPlanner.check` refuses symlinked destinations (`/tmp`) and misses
   symlink/case-insensitive `intoItself`** (`[Resolved in 7f5b3a0]`)
   - [OperationPlanner.swift](../../TwinPanesKit/Sources/TwinPanesCore/OperationPlanner.swift#L42-L63)
   - `metadata(of: destination)?.kind == .folder` uses `lstat`, rejecting symlinks to
     folders (e.g. typing `/tmp` in F5/F6 fails as `.destinationMissing`).
   - `folderPath(_:)` uses `standardizedFileURL.path` without resolving symlinks or volume
     case sensitivity, letting `/private/tmp/tree` into `/tmp/tree/sub` or `Tree` into
     `tree/sub` bypass `.intoItself`.
   - **Fix:** Resolve symlinks when checking destination kind/writability, and compare
     canonical paths (`BookmarkStore.canonicalPath` + volume case sensitivity) for
     `.folder` `intoItself`.

7. **`ItemNamer` accepts NUL bytes and rejects case-only renames on case-insensitive APFS** (`[Resolved in 7f5b3a0]`)
   - [ItemNamer.swift](../../TwinPanesKit/Sources/TwinPanesCore/ItemNamer.swift#L44-L51),
     [FileOperationSystem.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationSystem.swift#L178-L182)
   - Missing `name.contains("\0")` check lets `"foo\0bar"` pass validation and truncate at
     `\0` in C syscalls (`rename`/`mkdir`).
   - `metadata(of: target) != nil` rejects case-only renames (`"a.txt"` -> `"A.txt"`) as
     `.taken` on case-insensitive APFS, and `renamex_np(..., RENAME_EXCL)` also rejects
     same-entry renames.
   - **Fix:** Reject `name.contains("\0")` with `.notAName`; allow case-only same-entry
     renames when `BookmarkStore.pathsEqual(item, target)` and `name !=
     item.lastPathComponent` using `rename(2)` (or `FileOperationSystem.renameCaseOnly`).

8. **`RealFileOperationSystem.download` polls forever on offline/failing iCloud downloads** (`[Resolved in 7f5b3a0]`)
   - [FileOperationSystem.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationSystem.swift#L158-L169)
   - After `startDownloadingUbiquitousItem(at:)`, `while try metadata(of: url).isDataless`
     sleeps 100 ms forever without checking
     `URLResourceKey.ubiquitousItemDownloadingErrorKey` or
     `ubiquitousItemDownloadingStatusKey`. An offline or failing iCloud download hangs
     until manually cancelled.
   - **Fix:** Check `ubiquitousItemDownloadingErrorKey` (and
     `ubiquitousItemDownloadingStatusKey`) on each poll iteration and throw a
     `FileSystemError` when iCloud reports a download failure.

9. **Unbounded memory growth in `FileOperationQueue`, `FileOperationHistory`, `origins`,
   and 100k `CopyOutcome.finished` retention** (`[Resolved in d8de87b (core), 9ace114 (app)]`)
   - [FileOperationQueue.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationQueue.swift#L12),
     [FileOperationQueue.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationQueue.swift#L40),
     [FileOperationHistory.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationHistory.swift#L6-L7),
     [FileOperationHistory.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationHistory.swift#L80-L81),
     [TreeCopier.swift](../../TwinPanesKit/Sources/TwinPanesCore/TreeCopier.swift#L29),
     [FileOperationCommands.swift](../../TwinPanes/FileOperationCommands.swift#L17),
     [FileOperationCommands.swift](../../TwinPanes/FileOperationCommands.swift#L142)
   - `OperationResult.copied(CopyOutcome)` retains `CopyOutcome.finished: [String: URL]`
     (every item of a 100k-file copy, needed only transiently by `TreeMover`) permanently
     inside both `QueuedOperation.state` and `FileChange.result`, violating
     [PLAN.md](../PLAN.md) §3's bounded-memory constraint.
   - `FileOperationQueue.operations`, `FileOperationHistory.undoable`, and
     `FileOperationCommands.origins` also grow unboundedly for the app's lifetime.
   - **Fix:** Clear/omit `CopyOutcome.finished` before storing `.copied` results, cap
     `FileOperationHistory` depth (preserving delete-barrier semantics), and prune
     dismissed finished operations from `FileOperationQueue.operations` and `origins`.

10. **Undo/Redo history corruption on failed/cancelled undo and interleaved operations** (`[Resolved in ab34d75 (core), 9ace114 (app)]`)
    - [FileOperationHistory.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationHistory.swift#L85-L110),
      [FileOperationCommands.swift](../../TwinPanes/FileOperationCommands.swift#L161-L183)
    - `FileOperationCommands.undo` calls `history.didUndo(change)` unconditionally even if
      `.trash` or `.putBack` was cancelled, stopped at a conflict, or failed — discarding
      the undo entry and pushing an un-undone op onto `redoable`.
    - If a quick op (F7/F8) completes and calls `history.record(...)` (clearing
      `redoable`) while an async undo/redo is in flight, the finishing `didUndo`/`didRedo`
      resurrects stale `redoable` entries or appends out of order.
    - **Fix:** Track a monotonic history generation/epoch in `FileOperationHistory` so
      `record` invalidates in-flight `didUndo`/`didRedo`, and only file `didUndo` when all
      undo requests completed cleanly without cancellation or failures.

11. **Unbounded per-operation `DispatchQueue` allocation** (`[Resolved in d8de87b]`)
    - [FileOperationQueue.swift](../../TwinPanesKit/Sources/TwinPanesCore/FileOperationQueue.swift#L77)
    - `start(_:ask:)` allocates a brand-new
      `DispatchQueue(label: "FileOperationQueue.operation", qos: .userInitiated)` per
      operation. Concurrent immediate operations (`.trash`, `.delete`, `.rename`,
      `.makeFolder`) can spawn unbounded queues/threads, violating [PLAN.md](../PLAN.md) §3
      ("bounded background I/O (a small fixed pool, not unbounded tasks)").
    - **Fix:** Use one serial queue for serialized operations (`waitsItsTurn`) and a
      bounded `OperationQueue` (`maxConcurrentOperationCount: 4`) for immediate
      operations.

12. **Retain cycle leaks every `OperationRow` view hierarchy** (`[Resolved in f29dabc]`)
    - [OperationsStripViewController.swift](../../TwinPanesKit/Sources/BrowserKit/OperationsStripViewController.swift#L78-L82)
    - `row.onPause` captures `row` strongly (`row.show(operation)`), creating an
      `OperationRow -> onPause -> OperationRow` cycle so dismissed rows never deallocate.
    - **Fix:** Capture `[weak operation, weak row]` in `row.onPause`.

13. **Multi-selection drops rank-moving items on small live updates and desyncs when all
    selected items vanish** (`[Resolved in d607252]`)
    - [BrowserViewController.swift](../../TwinPanesKit/Sources/BrowserKit/BrowserViewController.swift#L175-L190),
      [BrowserViewController.swift](../../TwinPanesKit/Sources/BrowserKit/BrowserViewController.swift#L261-L284),
      [BrowserViewController.swift](../../TwinPanesKit/Sources/BrowserKit/BrowserViewController.swift#L306-L315)
    - In `applyRowChanges`, rank-moving updates arrive as `removed` + `inserted`.
      `tableView.removeRows` strips those rows from `selectedRowIndexes`; if any other row
      remains selected, `selectionChanged()` overwrites `selection` without the moved
      rows, and if none remain, only `priorName` is restored.
    - In `reloadKeepingSelection`, if the sole selected item vanishes (e.g. hiding
      `.hidden` via `⇧⌘.`) while `tableView.selectedRow` stays `>= 0` (now pointing to the
      next entry, e.g. `a.txt`), `restoreSelection` runs neither branch and
      `tableViewSelectionDidChange` doesn't fire — leaving the UI highlighting `a.txt`
      while `selection`/`selectedName` still hold `.hidden` (so F5–⇧F8 act on the vanished
      item). Same stale `ListingSelection.listing` bug occurs whenever numeric row indexes
      don't change across reloads.
    - **Fix:** Snapshot `selection` before `beginUpdates()` and restore
      `priorSelection.rows(in: item.listing)` (lead last) when any selected row was in
      `removed`. In `reloadKeepingSelection`, select row `0` (or replacement row) when
      `rows.isEmpty && lead == nil`, and always refresh `selection` against the new
      `item.listing`.

14. **Originating window closure breaks progress-strip transfer and wedges conflict sheets** (`[Resolved in f29dabc (strip refresh), 9ace114 (app)]`)
    - [FileOperationCommands.swift](../../TwinPanes/FileOperationCommands.swift#L122-L130),
      [FileOperationCommands.swift](../../TwinPanes/FileOperationCommands.swift#L139-L143),
      [FileOperationCommands.swift](../../TwinPanes/FileOperationCommands.swift#L164-L182),
      [FileOperationCommands.swift](../../TwinPanes/FileOperationCommands.swift#L281-L283),
      [OperationsStripViewController.swift](../../TwinPanesKit/Sources/BrowserKit/OperationsStripViewController.swift#L43)
    - `run`, `undo`, and `redo` strongly capture `controller` across `await ...finished()`,
      keeping `[weak controller]` in `origins[operation.id]` alive after `windowWillClose`
      removes it from `windowControllers`.
    - `window(of:)` never checks `windows().contains { $0 === controller }`, so it keeps
      returning the closed controller (whose `.window` is still non-nil). The strip row
      never moves to another window, and a conflict calls `beginSheetModal(for:)` on the
      closed window, wedging `ConflictBridge` and the serial queue.
    - Remaining windows' `OperationsStripViewController`s also only refresh on
      `queue.observe`, not on window closure.
    - **Fix:** Verify `windows().contains { $0 === controller }` in `window(of:)`, avoid
      strongly retaining `controller` across `await finished()`, remove
      `origins[operation.id]` on completion, expose `OperationsStripViewController.refresh()`,
      and refresh surviving strips when a window closes.

15. **`OperationPlanner.check` runs synchronously on `@MainActor` without destination
    `SecurityScope`, and retry sheets can present on closed windows** (`[Resolved in 9ace114]`)
    - [FileOperationCommands.swift](../../TwinPanes/FileOperationCommands.swift#L204-L224),
      [FileOperationCommands.swift](../../TwinPanes/FileOperationCommands.swift#L235-L250)
    - `askDestination` calls `OperationPlanner.check` synchronously on `@MainActor` before
      acquiring `FolderGrants` scopes. A destination covered by a saved bookmark (not
      currently open in a tab) has no active scope yet, so sandboxed `lstat`/`access` fail
      falsely, and slow/network volumes block the main thread (`AGENTS.md` Concurrency).
    - Retry sheets in `askDestination` (`again`) and `askName` (`Task`) call
      `sheet.begin(on: window)` without checking `window.isVisible` / controller
      membership in `windows()`.
    - **Fix:** Acquire deduplicated `SecurityScope`s for sources and destination, run
      `OperationPlanner.check` off the main actor while holding them, and guard
      `window.isVisible` (and open controller) before showing retry sheets.
