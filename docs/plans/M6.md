# M6 plan: NC keys and file operations

_Status: in progress (reviewed 2026-11-24; review decisions 5–8 approved as proposed)._

## Context

M5 left two panels with tabs, a sidebar, restoration and path completion. Each panel's
file list selects one row, and the browser can only look: nothing copies, moves,
renames, creates or deletes a file. F3 and F4 open the selected file; no other F-key
does anything, and there's no function-key bar.

PLAN.md §6, M6: a function-key bar, F2–F8 with ⌘ equivalents, an operations queue
(copy, move, trash, new folder, rename) with progress and conflict handling, a
cross-volume move that reports failures per item, and iCloud dataless files in
operations and at the editor's first edit. §4.7 sets the rules: `copyfile(3)` with
`COPYFILE_CLONE`, delete via `FileManager.trashItem`, a cross-volume move deletes the
source only after the copy is complete, F8 trashes and ⇧F8 deletes permanently with a
confirmation, and multi-selection is what F5–F8 act on. §5: a queued operation holds
its `SecurityScope` tokens until it ends, whatever happens to the tab that started it.

Items from §9 that land here:
- iCloud dataless files at the editor's first edit (from M3c, step 13);
- many files deleted under a shown 100k folder stall the tab (from M4): M6 deletes
  large trees itself, so it's measured here;
- the stall gate relaxed to 95 ms, to be tightened back in M6 (from M5).

**Done when:** copying and moving large trees is reliable, with cancel and conflicts:
- F5 and F6 copy and move the selection to the other panel through a confirm sheet,
  with progress, pause and cancel in the window;
- conflicts ask Replace, Skip, Keep Both (and Merge for folders), with Apply to All;
- a move across volumes deletes each source item only after its copy is complete, and
  lists the items that failed;
- F2 renames, F7 makes a folder, F8 trashes, ⇧F8 deletes after a confirmation;
- ⌘Z and ⇧⌘Z undo and redo the last file operations, as in Finder;
- the F-key bar shows the keys for what has focus and can be hidden;
- copying a 10,000-file tree keeps both panels under the stall gate.

All of it is proven in the smoke test on real files, except moving across volumes,
which needs a second volume the sandboxed smoke app can't mount (unit-tested through
the seam, checked by hand).

## Decisions

### D-a: multi-selection in the file list

- Standard macOS selection (§4.7): ⇧-click and ⇧-arrows extend, ⌘-click toggles, ⌘A
  selects all. The ".." row is never part of a selection that has other rows; ⌘A
  leaves it out.
- The selection is a set of names. Live updates, sorting and the hidden-files toggle
  keep it by name, as they keep the one selected name now (`namesToKeep` is already a
  set). Work over the names of a 100k selection runs off the main actor, like the rest
  of the pipeline (D39).
- The status line counts the selection ("3 of 120 selected, 1.2 GB" for files; folder
  sizes aren't counted).
- Restoration keeps saving one name, the focused row's, so `ItemState`'s browser
  version doesn't change.
- With nothing but ".." selected, F5–F8 act on nothing and beep; F2 on ".." beeps.

### D-b: the function-key bar

- A row of buttons along the bottom of the window, above the status line, as in §4.7's
  sketch: F1 to F10 with the title of the command each key runs for what has focus
  (F3 is "View" in a browser and "Find Next" in an editor, D9). Keys with no command
  there show a blank label.
- Built from the command registry (D21): each button sends its command's action
  through the responder chain, and is enabled by the same validation as the menu.
  Labels change when focus changes, along with the menus' key equivalents (§4.11).
- View › Hide Function Keys toggles it for every window. The choice is a user default;
  the M10 Preferences window will show it.
- WorkspaceKit owns it: it knows the registry and the focus chain, and nothing about
  files.

### D-c: the operations engine (TwinPanesCore)

- **Planning:** an operation first walks its sources off the main actor and builds a
  plan of items (files, folders, symlinks, packages as folders) with the total bytes
  and count, for progress. It refuses up front what can't work: a folder into itself
  or its own subfolder, a source that's gone, a destination without write access.
- **Copying:** each file goes through `copyfile(3)` with `COPYFILE_ALL`,
  `COPYFILE_CLONE` (an instant clone on the same APFS volume, a real copy elsewhere)
  and `COPYFILE_NOFOLLOW` (symlinks copy as links). Its progress callback reports bytes
  and is where cancel and pause take effect. Folders are created first and get their
  metadata (dates, xattrs) after their contents, so the copy's dates match the
  original.
- **Cancel** stops within the current file, removes that file's partial copy, and
  leaves what was already copied (listed in the operation's result). **Pause** holds
  the operation between chunks; the file stays open.
- **Moving:** on one volume, each top-level item is renamed (`rename(2)`, atomic). Across
  volumes (`EXDEV`), it's copied, the copy is checked (every file's size matches and
  `copyfile` reported success), and only then is that source item deleted. An item
  that failed anywhere keeps its source; the result lists it with its error.
- **Trash and delete:** F8 uses `FileManager.trashItem`, which also works sandboxed
  (M0 spike) and gives back where the item went (needed for undo). An item on a volume
  without a Trash fails with a message offering ⇧F8. ⇧F8 deletes permanently, deepest
  items first, after a confirm sheet saying it can't be undone.
- **Rename and new folder** are single `rename(2)` and `mkdir(2)` calls, refused if the
  name is taken or contains "/" (Finder's ":" rule doesn't apply to POSIX names).
- **The seam:** every change to the disk goes through a small protocol Core owns
  (`FileOperationSystem`: copy a file with progress, make a folder, rename, trash,
  remove, read metadata), with the real implementation and a test double that fails
  on chosen items, as `FileSystem` does for saves (D32). The planner reads through it
  too, so a test can simulate `EXDEV`, `ENOSPC`, `EACCES` and a volume vanishing.
- **Access:** an operation takes `SecurityScope` tokens for its sources' grants and
  its destination's when it's queued and holds them until it ends (§5). A destination
  without a grant asks for access as the path bar does (D42) before the operation is
  queued.

### D-d: conflicts

- A conflict is an item whose name is taken at the destination. The operation pauses
  and the window shows a sheet with both items (name, size, modification date, kind).
- Choices for a file: **Replace**, **Skip**, **Keep Both**. For a folder meeting a
  folder: **Merge** (go into it and continue, asking per item inside), **Replace**,
  **Skip**, **Keep Both**. A file meeting a folder or the reverse: Replace, Skip, Keep
  Both. **Stop** ends the operation. **Apply to All** remembers the choice for the rest
  of the operation, per kind (file or folder).
- **Replace moves the old item to the Trash**, not to oblivion, so undo can put it
  back. On a volume without a Trash, that Replace fails for the item and the old one
  stays (changed while building step 7: deleting it outright would lose data with no
  undo; the failure says why, and ⇧F8 then Copy again does it on purpose).
- **Keep Both** names the new item as Finder does: "name 2.ext", then "name 3.ext".
- Copying an item onto itself (both panels on one folder) offers only Keep Both and
  Skip.

### D-e: the queue and the progress strip

- One app-wide `FileOperationQueue` on the main actor holds every operation's state:
  planning, queued, running, paused, waiting for an answer, done, failed, cancelled.
- **Copy and move run one at a time**, in order, so two big copies don't fight over the
  disk; later ones show "Queued". Trash, delete, rename and new folder skip the queue
  and run at once: they're quick, and waiting behind a 50 GB copy to trash a file
  would feel broken. Undo and redo follow the rule of the operation they run.
- Progress reaches the main actor as `Sendable` snapshots at most 10 times a second,
  never per file.
- **The strip** sits above the F-key bar in the window that started the operation: one
  row per operation with what it does ("Copying 3 items to Backup"), a progress bar,
  bytes and items done, the time left once it's steady, and Pause and Cancel buttons.
  It's hidden when nothing runs. A finished operation leaves its row for a few seconds;
  one with failures stays, with a Show button that lists each item and its error.
- Closing the window or the tab that started an operation doesn't stop it (§5); its
  row moves to another window, or the app keeps it going without a row and asks before
  quitting while anything runs.

### D-f: the confirm sheets

- **F5 / F6:** "Copy 3 items to:" (or "Move") with an editable path field, filled with
  the other panel's folder: the folder of its front tab if that's a browser, otherwise
  of its most recently shown browser tab (D45 guarantees there is one). It takes a
  folder; `~` and paths relative to the current folder work, and a path that isn't a
  folder keeps the sheet open with a message. Return starts, Escape cancels. Changed
  while building step 14: renaming on the way (a single item's name in the field) and
  path completion in the field are left for later (PLAN.md §9): the engine copies under
  the source's name, and completion is wired to the browser's own path field.
- **F2:** a sheet with the name, selected without its extension, as Finder does.
- **F7:** a sheet with "untitled folder" selected; the new folder is selected in the
  list once it appears.
- **⇧F8:** "Delete 3 items permanently? This can't be undone." with Delete as a
  destructive button that needs ⌘D, Escape cancelling and Return doing nothing, as
  the app's other destructive sheets do (HIG).
- F8 asks nothing, as Finder's Move to Trash doesn't: undo brings the items back.
- Sheets are dialogs, which D7 allows. Rename and new folder use sheets rather than
  editing a row in place, so a live update can't pull the row out from under the
  field.

### D-g: undo and redo of file operations

- One app-wide history, as Finder keeps. Each finished operation records what it
  actually did, item by item, and how to undo it:
  - copy: trash the copies (not delete them);
  - move: move each item back; across volumes, that's a copy back and deleting the
    copy;
  - trash: put each item back from where `trashItem` sent it;
  - Replace (inside a copy or move): also put the replaced item back from the Trash;
  - rename: rename back;
  - new folder: trash it.
- A cancelled or partly failed operation records only the items it finished.
- Undo and redo run as operations: they show progress and meet conflicts like any
  other (say a new file now sits where an item would go back).
- ⌘Z and ⇧⌘Z reach the history while a browser has focus: the browser item answers
  `undo:` and `redo:` and validates them, with titles like "Undo Copy of 3 Items". The
  editor keeps its own undo (D28) while it has focus.
- ⇧F8 isn't undoable. It's recorded as a barrier: undo stops there, and the menu says
  "Can't Undo Delete".
- The history isn't saved across launches (Finder's isn't either).

### D-h: iCloud dataless files

- A file whose bytes live only in iCloud has `SF_DATALESS` set. The planner notes such
  files.
- **Copy, and move across volumes:** the file is downloaded first, through a
  coordinated read (`NSFileCoordinator`), then copied. The strip shows "Downloading"
  while it waits, and Cancel works during the download.
- **Rename, move on one volume, and trash** don't download: they never read the
  bytes.
- **The editor's first edit** (from M3c): the session's clone at the first edit (D34)
  waits for the download. The edit is held, the status line says "Downloading from
  iCloud…", and typing goes on into the held edit; a failed download leaves the session
  unedited with an error.
- CI has no iCloud, so the download sits behind an injected seam and is tested with a
  fake. A real evicted file is checked by hand.

## Default keys

Every F-key action also has a menu item and a ⌘ shortcut (§4.7). Proposed for review:

| Command | F-key | ⌘ shortcut | Menu |
|---|---|---|---|
| `browser.rename` | F2 | ⌘R | File › Rename… |
| `browser.view` (exists) | F3 | — | File › View |
| `browser.edit` (exists) | F4 | — | File › Edit |
| `browser.copyToOtherPanel` | F5 | ⇧⌘C | File › Copy to Other Panel… |
| `browser.moveToOtherPanel` | F6 | ⇧⌘M | File › Move to Other Panel… |
| `browser.newFolder` | F7 | ⇧⌘N (Finder) | File › New Folder… |
| `browser.trash` | F8 | ⌘⌫ (Finder) | File › Move to Trash |
| `browser.deletePermanently` | ⇧F8 | ⌥⌘⌫ (Finder) | File › Delete Immediately… |
| `view.toggleFunctionKeys` | — | — | View › Hide Function Keys |
| undo / redo | — | ⌘Z / ⇧⌘Z | Edit › Undo / Redo |

F10 quits per §4.7; it's added to the bar's map as `app.quit`. ⇧⌘N currently opens
nothing in a browser, so it's free; ⌘R is Finder's Show Original, which Twin Panes
doesn't have.

## Behaviour summary

| Action | Result |
|---|---|
| ⇧-click, ⌘-click, ⌘A in a file list | multi-selection, kept through live updates and sorting |
| F5 / F6 | confirm sheet with the other panel's folder; Return copies or moves |
| Name taken at the destination | conflict sheet; the operation waits |
| Copy or move running | a row in the strip with progress, Pause, Cancel |
| Cancel | stops within the current file; the partial copy is removed |
| Move across volumes | each source deleted only after its copy is complete |
| F2 / F7 | name sheet; the renamed or new item is selected |
| F8 | to the Trash at once |
| ⇧F8 | confirm sheet, then a permanent delete |
| ⌘Z / ⇧⌘Z in a browser | undo / redo the last file operation |
| View › Hide Function Keys | the bar goes away in every window |
| First edit of an evicted iCloud file | the edit waits for the download |

## Commits

Each commit is one logical change of about 250 lines at most. The order of work is
interface → failing tests → implementation. Each part ends with its smoke checks.

### Part A: selection and the F-key bar

1. **This plan**, after review.
2. **BrowserKit: multi-selection** (D-a). The table allows it; the selection is a set of
   names kept through live updates, sorting and the hidden toggle; ".." stays out;
   `BrowserItem.selectedEntries` for the commands; the status line counts it. Tests,
   including a 100k selection kept through a sort off the main actor.
3. **WorkspaceKit: the F-key bar** (D-b). Labels from the registry for the focused
   scope, buttons through the responder chain with validation, and the hide toggle.
   Tests through the dispatcher.
4. **Smoke: selection and the bar.** ⇧-arrows and ⌘A with real key events; the bar's
   F3 label changes between a browser and an editor; clicking its F3 opens the file;
   hiding it gives the panels the room.

### Part B: the engine

5. **Core: planning** (D-c). The walk, totals, refusals, and the
   `FileOperationSystem` seam with its real implementation. Tests on temp trees with
   symlinks, packages, an unreadable folder and a folder copied into itself.
6. **Core: copying** with progress, metadata, cancel and pause. Tests: a tree copies
   byte-exact with dates and xattrs; cancel removes the partial file; a fault on item n
   leaves the others; pause holds within a file.
7. **Core: conflicts** (D-d). Detection, each choice, Merge, Apply to All per kind,
   Keep Both naming, Replace to the Trash (the seam's trash in tests, so nothing lands
   in the real Trash), onto itself. Tests for each.
8. **Core: moving** on one volume and across (`EXDEV` from the seam): verify, then
   delete the source per top-level item; per-item failures. Tests, including a fault
   during the copy leaving the source untouched.
9. **Core: trash, delete, rename, new folder.** Tests, including a volume without a
   Trash and the deepest-first delete.
10. **Core: the queue** (D-e). States, copy and move one at a time, quick operations at
    once, scope tokens held to the end, throttled progress. Tests with a gated fake.
11. **Core: undo and redo** (D-g). Records from finished items, undo and redo through
    the queue, the ⇧F8 barrier, partial operations. A model-based test runs random
    operations, undoes them all and checks the tree is back.
12. **Core: dataless files in operations** (D-h). Download before copy and cross-volume
    move, none for rename and trash, cancel during the download. Tests with a fake.

### Part C: the UI

13. **BrowserKit: the progress strip** (D-e), hosted by the main frame as an optional
    bottom view controller, like the sidebar. Tests: rows follow the queue, Pause and
    Cancel reach it, failures stay with Show.
14. **BrowserKit: the confirm sheets** (D-f) for F5 and F6 (the destination field with
    completion and the access prompt), F2, F7 and ⇧F8. Tests drive the sheets.
15. **BrowserKit: the conflict sheet** (D-d). Tests.
16. **App: commands and menus.** The commands and keys above, the File and Edit menu
    items, Undo and Redo in a browser, the quit prompt while operations run. Tests
    through the dispatcher.
17. **EditorKit: the first edit of a dataless file** (D-h). Tests with the fake: the
    edit waits, typing continues into it, a failed download leaves it unedited.

### Part D: proving it

18. **Smoke: file operations with real keys.** In temp folders: F5 with the sheet
    copies a tree and the copy matches; a second F5 meets the conflict sheet and Keep
    Both, Replace and Merge each do their part; F6 moves; F2 renames; F7 makes a folder;
    F8 trashes and ⌘Z puts it back (the smoke test empties what it trashed); ⇧F8's sheet
    deletes; ⌘Z after a copy trashes the copy.
19. **Smoke: a large copy.** A 10,000-file tree with both panels watching its folders:
    under the stall gate throughout, cancelled halfway (no partial file left), then
    copied in full and verified.
20. **Smoke: deleting a 100k-file folder** permanently while the other panel shows it,
    under the stall gate (§9 from M4). If it stalls, the fix comes in its own commit
    before this one; the likely one is treating a vanishing shown folder as one event
    rather than reading its 100k removals.

### Part E: the stall gate and docs

21. **Smoke: tighten the stall limit** (§9 from M5). Read CI's last runs, lower the base
    from 95 ms toward 50 ms as far as all three runners stay under it, and record the
    readings in PLAN.md §9.
22. **Docs.** PLAN.md (decisions from D50 on, As built notes in §4.7 and §4.11, §9),
    README ("What it does today", "Where it's going") and DEVELOPMENT.md.

## Out of scope

- dragging files between panels, from or to Finder, and ⌘C / ⌘V of files (M13+ unless
  asked sooner)
- the preview pane and quick view (M7)
- NC-style marking (Insert, Space, + and −), batch rename, compare, archives (M13+)
- changing permissions or ownership, privileged operations (D14, Direct only)
- operations that survive a relaunch: a running copy is cancelled at quit after the
  prompt, and its partial file is removed
- the relaunch checks on macOS 15 (§9 from M5 stays open)
- user-editable key bindings and the Preferences window (M10)
