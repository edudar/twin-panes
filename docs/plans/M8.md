# M8 plan: insert and delete

_Status: reviewed 2026-11-27, all review questions settled; ready to start step 1. No
code yet._

## Context

After M7 the hex editor overwrites bytes only (D4): the piece tree already inserts and
deletes (`PieceTree.inserting`, `removing`, `replacing`, D26), but nothing above it
changes a file's length. M8 exposes that, because the text modes (M9a) need it (D12).

PLAN.md §6 (M8) asks for: insert/delete in the edit model, an insert-mode toggle in hex,
paste and delete of ranges, strategy A with a streamed rewrite (inode re-keying, new
backing generation, metadata kept), a free-space check, and a refusal or a copy-based
path where only strategy B is possible. §9 also moves *chunked `readSequential` for
fragmented piece trees* (from the M3a review) here.

What already holds and needs no work:
- **Re-keying and backing generations.** Strategy A swaps the file in and the registry
  re-keys the session (D32); pieces read the session's clone (D34), or the opened inode
  in a narrowed session (D33, D37), so nothing is rebased after a save of any length.
- **Metadata.** The swap keeps mode, xattrs, tags and creation date (M0 spike, `Saver`
  round-trip tests); M8 proves it for a save that changes the length.
- **Replay.** `JournalFormat.replay` already replaces a range with pieces of any length.
- **Viewers.** `HexView.contentLengthDidChange()` exists, and the editor and
  `ReadOnlyHexViewController` (D57) call it when a version's length differs.

What assumes a fixed length today, found while planning:
- `SavePlan` writes the whole file whenever the length differs: one byte appended to a
  4 GiB file rewrites 4 GiB.
- `performSave` skips the save when the plan has no ranges, which loses a pure truncation.
- `SessionJournal.record(from:to:)` uses `SavePlan.changedRanges`, which walks two trees
  of the same length; a different length records nothing useful.
- `SaveJournal` (strategy B) keeps the old bytes of the ranges written but not the old
  length, so it can't roll back a save that changes the size.
- `Saver` checks free space only when the clone fails; a cloned file that has most of
  its blocks rewritten needs that space too.
- `HexSelection` keeps the cursor on an existing byte (0 in an empty file): there is no
  position after the last byte, so nothing can be appended, and typing needs
  `layout.length > 0`.
- `HexView` has no `paste(_:)` or `cut(_:)`; ⌫ and ⌦ beep.

**Done when:** random edit sequences (insert, delete, overwrite, undo, redo, saves in
between) round-trip byte-exact through save; xattrs and tags survive a save that changes
the length; all of it proven in the smoke test on real files in the sandboxed app.

## Decisions

### D-a: one length-changing edit, `replace(range, with: bytes)` (`TwinPanesCore`)

`EditBuffer.replace(_ range:, with: Data)` and `EditorSession.replace(_:with:
selectionBefore:selectionAfter:coalescing:)` cover insert (empty range), delete (empty
bytes) and paste or typing over a selection, each one undo step journaled as today.
`overwrite` stays as it is (it checks the range lies in the file and keeps the length).
No separate `insert`/`delete` methods: three spellings of one tree operation would only
differ in their preconditions.

### D-b: a save writes from the first change to the end, not the whole file (`TwinPanesCore`)

`SavePlan` compares the saved and current trees position by position, as it does now,
over the length they share, then adds the current version's tail past that length; the
file is truncated to the new length. An insert at offset k rewrites `k..<length`, which
is the streamed rewrite of §4.3 (the bytes after k sit at new offsets, so a clone can't
keep them); an append writes only the new bytes; a delete at the end only truncates. The
whole file is still written when the disk no longer matches the saved identity (D31).

A plan that writes nothing but changes the length is not a no-op: `SavePlan` gets
`changesNothing` (no ranges and the same length), which `performSave` checks instead of
`ranges.isEmpty`.

Rewriting means reading many pieces in order. `EditSnapshot.readSequential` issues one
`F_NOCACHE` `pread` per piece; M8 measures a 4 GiB rewrite over a fragmented tree first
and coalesces runs of nearby `.original` pieces into chunked reads only if the
measurement shows it matters (§9 item, code-design rule 1). Numbers go in the commit.

### D-c: journaling a change of length (`TwinPanesCore`)

`SessionJournal.record(from:to:)` keeps its per-range records for trees of equal length.
For different lengths it writes one `replace(oldRange, newPieces)`: the stretch between
the longest common prefix and suffix of the two piece lists (compared by source and
offset). The format and replay don't change, so journals written by M3c–M7 builds stay
readable.

### D-d: strategy B rolls back a change of length (decided on review)

A hard-linked file saves in place (D35), and today's save journal can only put old bytes
back, not an old length. The journal gains the file's old length:
- **Format:** a new magic (`"TPS2"`) with the old size after the identity; the reader
  still accepts `"TPSJ"` journals (old size = current size), so a journal left by an
  earlier build still rolls back.
- **What it keeps:** the old bytes of every planned range that lies inside the old file.
  For an insert at k that is the old file's tail `k..<oldLength`, so the journal can be
  as large as the file; bytes past the old end have nothing to keep.
- **Rollback:** write the old bytes back, truncate to the old length, `F_FULLFSYNC`, as
  now plus the truncate. A journal with its commit mark is just deleted.
- **Free space:** the save needs room for the journal (old bytes kept) plus any growth of
  the file, checked before the journal is written (with D-e).

Whole-file plans (the disk no longer matches the saved version) still get Save As for
hard-linked files, as now.

### D-e: free space for the bytes a save writes (`TwinPanesCore`)

A cloned staging file shares blocks with the original until they're written, so a save
needs about `plan.byteCount` free bytes even after a successful clone (and the file's
whole size when the clone fails and it copies, as now). In place (D-d) it needs the
journal's old bytes plus the file's growth. `Saver` checks
`availableCapacity` against that before writing and throws `.notEnoughSpace` with both
figures; a failure leaves the file untouched, as every strategy-A failure does.

### D-f: save progress in the status line, no cancel (decided on review)

A rewrite of gigabytes takes seconds (minutes on USB). `Saver` reports bytes written
through a progress callback, at most every 100 ms on the main actor (as D53), and the
editor's status line shows "Saving… 37%". No cancel: undo after the save brings back
what was there, and quitting already waits for saves (`finishSaving`).

### D-g: insert mode, per tab, on by default (decided on review)

- A tab is in insert mode or overwrite mode. The mode is presentation state on
  `HexEditorItem`, saved with the tab (`ItemState` version bump, D47); new tabs start in
  insert mode, and tabs restored from an earlier build (no mode saved) too. Overwrite
  mode may be phased out later, so it stays a small switch around the same edit call
  (D-a), not a second editing path.
- **Toggle:** Edit › Insert Mode (a checkmark item, command ID `editor.insertMode`), the
  Insert key on keyboards that have one, and clicking the mode label in the status line.
  No new chord: macOS has none for this, and the free ones near it clash with Finder's
  Go menu (⇧⌘I) or the inspector (⌥⌘I). Feedback rule: standard shortcuts first.
- **Status line** shows "Overwrite" or "Insert" after the offset.
- **The cursor** (`HexSelection`): in insert mode it may also sit at `length`, after the
  last byte, and an empty file has that one position; overwrite mode clamps it back to
  the last byte. The insert-mode cursor is drawn as a bar before its byte instead of a
  box, so the mode shows where the user looks.

### D-h: what each key does in each mode (decided on review)

| Action | Overwrite mode | Insert mode |
|---|---|---|
| Hex digit | as now: high nibble, then low nibble | first digit inserts `d0` before the cursor (cursor stays, low nibble pending), second sets the low nibble; one undo step |
| Text character | as now | inserts its byte before the cursor |
| Typing with a selection of 2+ bytes | as now (starts at its first byte) | replaces the selection |
| ⌫ | zeroes the selection if 2+ bytes, else the byte before the cursor, and moves the cursor onto it | deletes the selection if 2+ bytes, else the byte before the cursor |
| ⌦ | zeroes the selection, or the byte under the cursor and moves to the next | deletes the selection, or the byte under the cursor |
| Edit › Cut (⌘X) | copy, then zero the selection | copy, then delete the selection |
| Edit › Paste (⌘V) | overwrites from the selection's start; refused (beep, status) if it would run past the end | replaces the selection (inserts at the cursor when it's one byte or at the end) |
| Edit › Delete | zeroes the selection | deletes the selection |

Overwrite mode keeps its promise that the length never changes: what insert mode
deletes, it sets to `00` (D-j). Typing coalescing (2 s, same column, continuing at the
cursor) applies in both modes, and a run of ⌫ or ⌦ joins one undo step the same way.

### D-j: zeroed bytes cost nothing to store (`TwinPanesCore`)

Zeroing a 4 GiB selection through the add buffer would write 4 GiB to it. `Piece.Source`
gains `.zeros`: a piece that reads as `00` bytes and has no backing file, so zeroing any
range is one O(log n) tree edit (`EditBuffer.zero(_ range:)`, `EditorSession.zero`).
- Snapshot reads fill zeros; the dirty highlight shows them like any edit; `SavePlan`
  writes them like any other source.
- Two `.zeros` pieces that touch merge (their offset is unused and stays 0, so
  `continues` checks the source only for `.zeros`).
- The journal encodes the source as `2`. A journal holding one can't be replayed by an
  M7 build, which reads it as damaged and stops there; going back a build is not
  supported, so that's accepted.

### D-i: what Paste reads (proposed)

- **Hex column:** pairs of hex digits, with whitespace, `0x` prefixes and commas between
  them ignored, so what Copy writes (`4F 2A 9C`) and C-style arrays paste back. Anything
  else, or an odd number of digits, is refused with a status message.
- **Text column:** the pasteboard's string encoded in the column's encoding (ASCII or
  Latin-1); a character it can't hold refuses the whole paste and names it, as typing
  does.
- **Size:** up to `HexCopy.maxBytes` (16 MiB) of bytes, parsed on the main actor
  (measured; moved off it if it stalls). Larger pastes are refused with a message; a
  pasteboard that big is already in memory, and appending it to the add buffer on the
  main actor would stall. "Insert from file…" for big inserts is logged in §9.

## Commits

Each at most 250 changed lines, verified alone, stopping for review before each commit.

### Part A: the model and the save path (`TwinPanesCore`)

1. **Core: `SavePlan` for length changes** (D-b): shared-length comparison plus the
   tail, `changesNothing`, and `performSave` using it. Tests: insert/append/delete at the
   start, middle and end; truncation-only saves; random trees against a byte model.
2. **Core: journal records for length changes** (D-c). Tests: replay equals the live tree
   after random sessions of insert, delete, overwrite, undo, redo and saves; an M3c
   journal still replays.
3. **Core: `EditBuffer.replace` and `EditorSession.replace`** (D-a): undo with
   selections, coalescing, journaling, read-only refusal, the first-edit clone. Fuzz
   against a `[UInt8]` model with undo and redo.
4. **Core: the save journal keeps the old length** (D-d): the `"TPS2"` format, reading
   `"TPSJ"`, rollback with truncation, and `Saver` saving length changes in place.
   Tests: grow, shrink and insert-at-start saves of a hard-linked file, rolled back from
   a journal without its mark; an old-format journal still rolls back.
4b. **Core: free space** (D-e) after a clone and for the in-place journal, through the
   `FileSystem` seam with a fake capacity.
4c. **Core: zero pieces** (D-j): the `.zeros` source in the tree, snapshot reads, the
   journal format and `EditorSession.zero`. Tests: merging, every read path, replay,
   fuzz against the byte model with zeroing mixed in.
5. **Core: save progress** (D-f): the callback in `Saver`, throttled on `EditorSession`,
   and a session change for it.
6. **Core: chunked sequential reads**, only if the measurement in D-b says so; otherwise
   the numbers go in PLAN.md §9 and the step is dropped.

### Part B: the view (`HexViewKit`)

7. **HexViewKit: the position after the last byte** (D-g): `HexSelection` with an end
   position in insert mode, the bar cursor, empty files. Tests: moves, selections and
   clamping when the mode switches.
8. **HexViewKit: typing in insert mode** (D-h): an edit request type
   (`range`, `bytes`, `column`, `cursorAfter`) replacing the overwrite-only delegate
   call, the two-digit insert, typing over a selection.
9. **HexViewKit: ⌫, ⌦, Cut, Delete and Paste** (D-h, D-i), with the paste parser as its
   own tested type and menu validation per mode.

### Part C: the editor and the app (`EditorKit`, app target)

10. **EditorKit: insert mode on the tab** (D-g): the mode, its status-line label and
    click, restoration of the mode, and edits sent to `session.replace`.
11. **EditorKit: save progress in the status line** (D-f).
12. **App: Edit › Insert Mode, Cut, Delete** in the menu and command catalog, and the
    Insert key.

### Part D: proving it

13. **Tests: round trip through save**: random edit sequences with saves in between on
    real temp files, comparing the file to the model after every save; a save after
    undoing across a length-changing save; xattrs, Finder tags, mode and creation date
    after a save that grows and one that shrinks a file.
14. **Tests: the fault suite for length changes**: a kill or power loss at every
    operation of a length-changing save, strategy A and B, leaves the old or new
    contents (length included) after recovery's rollback.
15. **Smoke: insert and delete in the running app**: the real menu toggles insert mode;
    typing in both columns at the start, middle and after the last byte; ⌫, ⌦, Cut and
    Paste through the real menu; undo and redo; save, and the file on disk matches; a
    dirty session's length change shows in QuickView. On a 4 GiB sparse file: a byte
    appended and the last bytes deleted save near-instantly (plan check, no rewrite), and
    a byte inserted at the start of a 256 MiB real-data file saves with progress shown.
    A full 4 GiB rewrite is timed by hand, not on CI (runner disk space).
16. **Docs**: PLAN.md decisions (D61 on), §4.2, §4.3 and §4.4 As built notes (strategy
    B now changes lengths, replacing §4.3's "insert/delete … refused"), the M8 row, §9
    (big pastes, the chunked-read result, overwrite mode possibly phased out); README
    (what works); this file's status.

## Out of scope

- Find/replace in hex (M9a, any length, D19).
- Text and Markdown modes (M9a–M9c).
- Whole-file saves of hard-linked files (the disk no longer matches): Save As, as now.
- Cancelling a running save (D-f; undo covers it).
- Pastes over 16 MiB and inserting a file's contents (D-i).
- Marking where bytes were deleted (the dirty highlight shows inserted and overwritten
  bytes only, as before).
- Editing in QuickView or the preview pane (D57).
