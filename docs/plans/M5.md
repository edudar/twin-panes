# M5 plan: dual panels and tabs

_Status: in progress since 2026-11-24. Steps 1a to 14 done; step 15 built, awaiting review._

## Context

M4 left a browser that lists, sorts, filters and live-updates a 100k-file folder in one
panel. The workspace model already has both panel slots: `MainFrameLayout` keeps tabs,
a selection and an active panel per slot, and `MainFrameViewController` draws a tab bar
per panel, but hides the right panel until something is put there. Nothing is restored
on relaunch, and there's no sidebar.

PLAN.md §6, M5: a second panel, active-panel focus, a tab bar per panel, tab restore on
relaunch through AppKit restoration (D23), a collapsible sidebar (Favorites,
Locations), shell-style path completion in the path field (§4.7), and a relaunch smoke
test that also checks crash recovery. Items from §9 that land here:
- bookmarks resolving after a relaunch, automated (from the M0–M2 review);
- the crash smoke test with a child process (from M3c);
- volumes in the sidebar (from M4);
- `browser.switchPanel`, left out of the menus until dual panels exist (§4.11).

**Done when:** daily navigation works without Finder:
- two panels with their own tabs, switched with Tab and by clicking;
- the sidebar's favorites and volumes open in the active panel;
- quitting and relaunching brings back every window's panels, tabs, folders, history,
  sort order and hidden-files setting;
- a crash while editing brings the edits back in their own restored tab;
- path completion works in a 100k-file folder under the stall limit.

All of it is proven in the smoke test, including two real launches of the app.

## Decisions (proposed)

### D-a: two panels, always

- Every new window opens with a browser tab in each panel. The right panel starts in
  the left panel's folder (as Far Manager does on a first run), so F5 and F6 (M6) have a
  destination from the start.
- A panel is never empty. When its last tab is a browser, that tab can't be closed or
  moved to the other panel: ⌘W and Move Tab to Other Panel are disabled for it, and a
  drag out of the tab bar is refused. When its last tab is anything else, closing or
  moving it opens a browser tab in its place, at the other panel's folder. ⌘W never
  closes the window; the window's close button and ⇧⌘W do, through the close workflow
  as today.
- The split is two equal halves at first; the divider is draggable, and its position
  is restored (D-c).

### D-b: the active panel follows focus

- Clicking into a panel, or anything moving keyboard focus into it, makes it active
  (`MainFrameLayout.activate`). Panel commands (new tab, close tab, next tab) act on the
  active panel, as they already do.
- The active panel's tab bar is drawn as active. The other panel's file list shows its
  selection unemphasized, which `NSTableView` does on its own when it isn't first
  responder.
- **Tab and ⇧Tab switch panels** only while a file list has focus (§4.11): bound as
  `panel.switch` in the file list's command scope, not the browser's, so the path
  field and the editor keep Tab. Switching focuses the other panel's selected item.
- **Moving tabs:** a tab can be dragged onto the other panel's tab bar (or reordered
  within its own), and Window › Move Tab to Other Panel does the same from the
  keyboard (no default key until M10). Both use `MainFrameLayout.move`, so the item
  isn't recreated.

### D-c: restoration through AppKit, with our own versioned state

- **State model (WorkspaceKit):** `ItemState` is `{ kind, version, payload: Data }`.
  `WorkspaceItem` gains `restorableState: ItemState?`; nil means the item isn't
  restored (placeholders). `WindowState` holds each panel's item states and selected
  index, the active panel, the divider position, the sidebar's width and whether it's
  shown, and the zoomed item. All of it is `Codable`.
- **Restoring items:** an `ItemRestorer` maps a kind to a factory and the newest
  version it reads. The type is in WorkspaceKit, so its rules are unit-tested; the app
  registers the factories. A kind it doesn't know, or a version newer than the build,
  is skipped, never misread. A window that restores no items gets the default two
  browsers. A `WindowState` written by a newer build is refused as a whole.
- **AppKit's part:** each main window is restorable, with a `restorationClass` that
  rebuilds its controller. `encodeRestorableState(with:)` writes the `WindowState` as
  JSON under one key, and layout changes call `invalidateRestorableState()`. AppKit
  decides whether to restore at all (the "Close windows when quitting an app" setting,
  D23).
- **Browser state:** the folder's path, the back and forward history as paths, the sort
  order, the hidden-files setting and the selected names. Access comes from the saved
  folder grants (D42), so a tab needs no bookmark of its own. A folder that's gone
  opens its nearest existing ancestor, with a status message.
- **Editor state:** the file as a security-scoped bookmark, the cursor and scroll
  offset, and the view options. Restored editors are always clean: dirty sessions
  either got saved or discarded at quit, or come back through crash recovery.
- **Crash recovery meets restoration:** recovery scans the session folders in
  `applicationWillFinishLaunching` and adopts each recovered session into the
  `SessionRegistry` without showing it. AppKit then restores windows, and a restored
  editor tab for that file gets the recovered session from the registry, just as
  opening an open file does today. In `applicationDidFinishLaunching`, recovered
  sessions that no restored tab claimed open in new tabs, as they do now (§4.8).
- **The smoke test never touches the user's saved state.** In `--smoke-test` and
  `--bench` mode windows aren't restorable. The relaunch check (D-f) goes through the
  same `WindowState` encoding but keeps it in a file in its temp folder. A unit test
  covers the AppKit half: encoding a real window's state into an `NSKeyedArchiver` and
  restoring a window from it.

### D-d: the sidebar

- A source list (`NSOutlineView`, sidebar style) to the left of the panels, in a split
  view item that collapses. View › Show/Hide Sidebar with ⌃⌘S, as in Finder. Its width
  and visibility are per window and restored.
- **Favorites:** by default Home, Desktop, Documents, Downloads and Applications. Kept
  as paths in user defaults, not bookmarks, because access comes from folder grants:
  clicking a favorite without a grant asks for access as the address bar does (D42).
  Folders are added by dragging them in, removed from the context menu, and
  reordered by dragging.
- **Locations:** the mounted volumes the system shows (not hidden or internal ones),
  updated live from `NSWorkspace`'s mount, unmount and rename notifications. Removable
  and ejectable volumes get an eject button (`NSWorkspace.unmountAndEjectDevice`). If
  the sandbox refuses ejecting, the button is left out and that's logged in §9.
- **Clicking** opens the location in the active panel's browser. If the active panel
  shows an editor, it opens in a new browser tab in that panel. The row for the active
  panel's folder is highlighted.
- **Where it lives:** BrowserKit owns the sidebar's view controller and reports clicks
  through a closure. WorkspaceKit only hosts an optional leading view controller, and
  the app connects the two. WorkspaceKit doesn't gain a sidebar protocol.

### D-e: path completion (§4.7)

- **Matching (TwinPanesCore, no AppKit):** `PathCompletion` takes the typed text, the
  real home folder and the names in the folder being completed. It returns the
  longest shared prefix, whether the single match is a folder (which gets a trailing
  `/`), and the sorted matches. The rules are §4.7's, so the tests cover each:
  - `~` expands to the real home folder;
  - matching is case-insensitive;
  - hidden names are offered only when the typed name starts with `.`;
  - folders sort first.
- **Names:** a small cache, owned by the open field, reads one folder's names off the
  main actor with the lister's cheap keys and keeps them while the field is open. A
  folder without a grant has no names, and nothing prompts for access.
- **In the field:** the first Tab inserts the shared prefix. If the folder isn't read
  yet, the prefix is inserted when the names arrive, provided the text hasn't changed
  meanwhile. A second Tab with several matches opens AppKit's own completion list
  (`NSTextView.complete(_:)` through the field delegate's `completions` method): the
  arrow keys, Return and Escape come from AppKit, and VoiceOver reads the list.
  Escape with no list open closes the field, as today.

### D-f: two launches in the smoke test

- The smoke test runs the app's own executable as a child process twice, with
  `--smoke-child <step> <folder>`. Each child writes a JSON report into the folder
  for the parent to check.
  1. **Restore:** the first child sets up two panels with several tabs, a history, a
     sort order, hidden files shown and an editor at an offset, writes its state and
     quits. The second child restores from that state and reports what it shows,
     including whether the folders' grants and the editor's bookmark resolved
     (the §9 item).
  2. **Crash:** a child edits a temp file with real key events, using a sessions
     folder inside the test folder, and reports once its journal is flushed. The
     parent kills it with SIGKILL. A second child restores and recovers; its report
     must show the edits in the restored tab, dirty.
- First commit of the part: check that a sandboxed app may launch its own executable
  (the child inherits the sandbox). If it may not, the two launches move into the CI
  workflow as two steps, and the plan is updated before going on.

## Behaviour summary

| Action | Result |
|---|---|
| New window | a browser tab in each panel, both at the same folder |
| Tab / ⇧Tab in a file list | the other panel becomes active and focused |
| Click in a panel | that panel becomes active |
| ⌘T, ⌘W, ⌃Tab | act on the active panel; ⌘W is disabled on a panel's last browser tab, and on any other last tab leaves a browser in its place |
| Drag a tab to the other tab bar | the tab moves there, keeping its state |
| Window › Move Tab to Other Panel | the same, from the keyboard |
| ⌃⌘S | shows or hides the sidebar |
| Click a favorite or volume | opens it in the active panel |
| Eject button | ejects the volume; its tabs show the missing-folder state as today |
| Quit, relaunch | every window comes back with its panels, tabs and browser state |
| Crash while editing, relaunch | the restored tab has the edits, dirty |
| Tab in the ⇧⌘G field | completes the name; a second Tab lists the matches |

## Commits

Each commit is one logical change of about 250 lines at most. The order of work is
interface → failing tests → implementation. Each part ends with its smoke checks.

**Part A: two panels**
1. **This plan**, after review.

   1a. **WorkspaceKit: the status line shows the item in front.** Added while building
   step 2: a browser in the other panel (or a tab behind) posted its own status on every
   live update and overwrote the active tab's. Each item gets its own host, which passes
   messages on only while the item is the zoomed one or the active panel's tab. Lands
   before step 2, so step 2's smoke checks don't race.
2. **WorkspaceKit: both panels always.** Both panels start as equal halves. New windows get a browser in each panel; a
   panel's last browser tab can't be closed or moved out, and any other last tab is
   replaced by a browser at the other panel's folder when it goes.
   Tests on `MainFrameLayout` and the frame.
3. **WorkspaceKit: the active panel follows focus**, and the active tab bar is drawn
   as active. Tests move the first responder between panels.
4. **Commands: `panel.switch`** (Tab and ⇧Tab in the file list's scope) and Move Tab
   to Other Panel. Tests through the dispatcher, including that Tab in the path field
   and the editor isn't taken.
5. **WorkspaceKit: dragging tabs** within a tab bar and onto the other one. Tests on
   the drop logic. A synthesized drag isn't reliable, so the drag itself is checked by
   hand.
6. **Smoke: two panels.** A new window shows both panels; Tab and ⇧Tab and clicks
   switch them, with real events; a tab moves with the menu command. Built along with
   steps 2 to 4, each with its own checks, so this step only adds what step 5 needs.

**Part B: restoration**
7. **WorkspaceKit: `ItemState` and `WindowState`.** Encoding and decoding the layout.
   Tests: round trip, an unknown kind and a newer version are skipped, an empty
   result falls back to the default. `WindowState` holds the tabs only; the divider
   comes with step 10 and the sidebar with part C, as optional fields, so older state
   still decodes.
8. **BrowserKit: browser state.** Folder, history, sort, hidden files and selection;
   a missing folder opens its nearest ancestor. Tests on real temp folders. As built:
   the selection is one name, as the file list selects one row; a folder the sandbox
   needs access for counts as there, so the tab shows its access prompt instead of
   moving up. Proven in the real app by the restore relaunch (step 13).
9. **EditorKit: editor state.** Bookmark, cursor, scroll and options. Tests. As built:
   EditorKit saves and decodes the state and puts back the view (`restoreView`), clamped
   to the file as it is now; opening the file through the session registry is the app's
   part, in step 10. `HexView` gains `topRow` and `scroll(toTopRow:)`.
10. **App: AppKit restoration.** Restorable windows, encoding and restoring,
    invalidation on layout changes, and no restoration in smoke and bench mode. A unit
    test round-trips a window through a keyed archiver. Built as two commits:
    - 10a. **WorkspaceKit:** `WindowState` goes in and out of AppKit's restorable-state
      coder as one JSON value and gains the divider position; the main frame saves and
      restores tabs and divider, and invalidates the window's state on every layout
      change and divider drag.
    - 10b. **App:** the restoration class, the browser and editor factories, and no
      restoration in smoke and bench mode.
11. **App: recovery meets restoration** (D-c). Tests that a recovered session is
    claimed by a restored tab, and opens in a new tab otherwise. As built: the registry
    holds sessions weakly, so `LaunchRecovery` (TwinPanesCore) holds the recovered
    sessions from `applicationWillFinishLaunching` until windows are restored, then hands
    back the unclaimed ones and lets go. The tests are on it; the app's part is proven by
    the crash relaunch (step 14).
12. **Smoke: can the app launch itself sandboxed?** The check from D-f. The plan is
    updated with the answer. Answer (2026-11-24, dev Mac): yes. The app's executable
    started with `Process` runs, inherits the sandbox, writes its report and quits, so
    the relaunch checks stay in the smoke test as planned. A second instance through
    LaunchServices (`NSWorkspace.openApplication`) sent no report within 20 s; it isn't
    needed, so it wasn't pursued. CI's runners must agree (checked on the next push).
13. **Smoke: the restore relaunch** (D-f, 1). As built: the first child browses, sorts,
    shows hidden files, opens an editor in the right panel and writes its window state
    to a file; the second restores from it and reports the tabs, active panel, folder,
    selection, history, sort order, hidden files, and the editor's file, selection, row
    width and clean state. It found that a restored editor lost its selection and scroll
    (restored before its view loaded), fixed in its own commit before this one. The
    editor's bookmark resolving after a relaunch is now automated (§9, from the M0–M2
    review); a folder grant isn't, since the smoke test has no user-granted folder.
14. **Smoke: the crash relaunch** (D-f, 2). As built: each child keeps its sessions in
    the test folder. The first types a byte into an editor with real key events, saves
    its window state and reports; journal records are written at once, so the parent
    kills it with SIGKILL as soon as the report is there. The second runs the launch
    flow (`LaunchRecovery`, restore, unclaimed sessions) and reports one recovered
    session, claimed by the restored tab, dirty, with the typed byte. This closes the
    §9 crash smoke test (from M3c).

**Part C: the sidebar**
15. **Core: favorites and volumes.** The favorites list in user defaults (in an
    absolute-path suite in tests) and the volume list with its changes. Tests. As
    built: `Favorites` and `MountedVolumes`, which picks what Finder shows (browsable,
    the boot volume or not internal; boot volume first). Watching for mounts uses
    `NSWorkspace`, so it lands with the sidebar in BrowserKit (step 18).
16. **BrowserKit: the sidebar view.** Sections, clicking and highlighting the active
    folder. WorkspaceKit hosts it, and ⌃⌘S toggles it. Tests.
17. **BrowserKit: editing favorites.** Drag in, remove, reorder. Tests.
18. **BrowserKit: ejecting**, if the sandbox allows it, and live mounts. Tests with an
    injected volume list. A real eject is checked by hand.
19. **Smoke: the sidebar.** Toggling it, clicking a favorite and the boot volume to
    navigate the active panel, and adding and removing a favorite.

**Part D: path completion**
20. **Core: `PathCompletion`.** The matching rules, with tests for each rule and
    randomized names against a simple model.
21. **Core: the names cache** off the main actor. Tests: one read per folder, a
    superseded read is dropped, no grant means no names.
22. **BrowserKit: Tab in the path field** (D-e). Tests drive the field editor.
23. **Smoke: completion with real key events**, including in the 100k folder under
    the stall gate.

**Part E: docs**
24. **PLAN.md** (decisions D45 onwards, As built notes in §4.7, §4.8 and §4.11, §9
    updates), README and DEVELOPMENT.md.
